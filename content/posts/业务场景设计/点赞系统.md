1. 业务功能有哪些
2. 架构的核心目的是什么？
   1. 用户交互体验
      1. 对架构**功能复杂度**要求不高，不过可用性要求极高，所以需要做好**降级**。
   2. 延迟
      1. 交互对了，写延迟几秒才能同步完全没问题
      2. 读要尽量快，也就是使用缓存，甚至多级缓存。
   3. 高QPS
      1. 要保证高吞吐，像b站这种程度读300k/s，写15k/s，一定要上缓存和消息队列。除了冷热分离，必须强调 **“多级缓存（Local Cache）”** 和 **“热点治理”**。
         1. 热指cache，尽量让读操作放在cache中，这样才能保证吞吐。
         2. 增加本地缓存，减少热点数据对redis等的压力
            1. 本地缓存需要较短的过期时间
   4. 缓存一致性
      1. **策略上**是最终一致性，但**工程实现上**需要“巧妙的设计”来保证**数据不丢**。

3. 架构迭代方式
   1. mysql实现必要业务功能，自己的项目可以减少一些功能，只保留必要的
   2. 通过redis旁路缓存增加读能力，使用zset方便查看点赞列表
   3. 写操作完全不走db，热点数据全在redis中，通过定时任务同步到mysql（冷数据）
   4. 写数据打到mq，读数据使用多级缓存



在微服务架构设计中，尤其是像点赞这种**高并发、通用型**的基础服务，**绝对不要**去调用业务服务（如视频服务）来校验 video_id 是否存在。

防止黑客刷接口，是 **网关层（Gateway / WAF）** 和 **风控层** 的责任，不是业务逻辑层的责任。

- 应该通过 IP 限流、User-ID 频率限制、Token 校验来拦截黑客。

> **查询分页**
>
> 对一个视频下的所有评论进行点赞，假设上限为999；
>
> 如果查询这个点赞列表采用的是游标分页，那么点赞列表的记录就一定需要有一个标识用于分页；
>
> 如果查询这个点赞列表适用的是全量返回，那么超过999的数据页的评论点赞记录就会消失；
>
> 因此这里极大可能是<u>redis+db数据回溯</u>的方式；
>
> 仅记录前999条，从第999条开始的数据查询数据库，数据再以<u>短时效保存到临时缓存</u>中；

常用的状态下点赞、取消点赞都是存在一个最新的zset中，此处查询点赞列表的冷数据放在一个临时的zset中，这样不会对真正“新”的数据有所干扰，并且如果进行操作也可以正常进行。设置的临时zset过期时间较短，这样也不会对内存造成太大的压力。

### 监听Binlog

#### 一、 核心原理：它是如何工作的？

MySQL 的 Binlog 记录了所有的 DDL 和 DML 语句。监听 Binlog 的工具本质上是**把自己伪装成一个 MySQL Slave（从库）**：

1. **伪装：** 监听工具向 MySQL Master 发送 dump 请求。
2. **拉取：** Master 认为它是从库，会将 Binlog 事件实时推送给它。
3. **解析：** 工具解析二进制流，将其转化为结构化的数据（JSON 或对象），包含：哪个表、什么动作（Insert/Update/Delete）、旧值、新值。

#### 监听工具

- canal

  - **canal [kə'næl]**，译意为水道/管道/沟渠，主要用途是**基于 MySQL 数据库**增量日志解析，提供增量数据订阅和消费

  - 工作流程

    1. Canal连接到mysql数据库，模拟slave
    2. canal-go与Canal建立连接
    3. 数据库发生变更写入到binlog

    5. Canal向数据库发送dump请求，获取binlog并解析

    4. canal-go向Canal请求数据库变更

    4. Canal发送解析后的数据给canal-go

    5. canal-go收到数据，消费成功，发送回执。（可选）

    6. Canal记录消费位置。

  - [quickstart](https://github.com/alibaba/canal/wiki/QuickStart)

- debezium

  - Debezium是一个开源项目，为捕获数据更改(change data capture,CDC)提供了一个低延迟的流式处理平台。你可以安装并且配置Debezium去监控你的数据库，然后你的应用就可以消费对数据库的每一个行级别(row-level)的更改。
    - 只有已提交的更改才是可见的，所以你的应用不用担心事务(transaction)或者更改被回滚(roll back)。
    - Debezium**为所有的数据库更改事件**提供了一个统一的模型，所以你的应用不用担心每一种数据库管理系统的错综复杂性。
    - 另外，由于Debezium用持久化的、有副本备份的日志来记录数据库数据变化的历史，因此，你的应用可以随时停止再重启，而不会错过它停止运行时发生的事件，保证了所有的事件都能被正确地、完全地处理掉。
  - 适用于
    - 缓存失效(Cache invalidation)
    - 简化单体应用(Simplifying monolithic applications)
    - 共享数据库(Sharing databases)
    - 数据集成(Data integration)
    - 命令查询职责分离(CQRS)
